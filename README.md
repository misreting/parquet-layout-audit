# parquet-layout-audit

Audit Parquet files for the physical layout problems that quietly turn off
row-group pruning: too many or too few row groups, missing statistics, and
-- the biggest and least-known cause -- unsorted data.

```
$ parquet-layout-audit orders_2024.parquet

orders_2024.parquet
  30,082,905 bytes, 2,000,000 rows, 20 row group(s)
  row groups: avg 100,000 rows / 1,503,872 bytes (min 1,503,406, max 1,504,352)
  columns:
    event_id (INT64): 20/20 have stats, dictionary
      pruning: prunes 0.0 of 20 row groups on average for an equality filter
      on an observed value (row-group ranges overlap 100% of the time pairwise)
  Findings (0 error, 1 warning, 0 info):
    [WARNING] PLA004 event_id: prunes 0.0 of 20 row groups on average for an
        equality filter on an observed value -- effectively unsorted: an
        equality filter must open almost every row group
        remedy: sort by `event_id` before writing (or partition/cluster
        writes by it); this file currently prunes 0.0 of 20 row groups
        for that column
```

That's this tool against a real file generated by
[`examples/measure_evidence.py`](examples/measure_evidence.py). The same
2,000,000 rows, sorted before writing instead of shuffled, produce
`prunes 19.0 of 20` for the identical column -- and DuckDB, queried
directly against both files with the same selective filter, reads **7.3x
more bytes** from the unsorted one. Nothing in this README is invented;
every number is real output, reproduced below in full.

## The problem

Parquet's speed on selective queries comes from **row-group pruning**: each
row group carries min/max statistics per column, and a reader can skip a
whole row group without decompressing it once those statistics prove the
filter can't match anything inside. That guarantee depends entirely on how
the file was laid out, and most files written with default settings lay
out badly in one of a few specific ways:

- **Unsorted data.** If a column's values were written in random order,
  every row group's range ends up spanning nearly the whole domain, so no
  value can ever be ruled out anywhere -- every row group must be opened
  regardless of the filter. This is the single biggest and least-known
  cause of slow Parquet, because the file still "has statistics" and looks
  fine on casual inspection; the statistics just can't prune anything.
- **Missing statistics.** Without min/max per column chunk, pruning can't
  happen at all, full stop -- the reader must decode everything.
- **Too many or too few row groups.** Thousands of tiny row groups mean
  per-group overhead (footer entries, open/seek cost) dominates; one
  enormous row group means there's no pruning granularity to speak of, no
  matter how well-sorted the data is.
- **Too many small files.** Splitting a dataset across many small files
  adds the same kind of per-file overhead, one level up.
- Dictionary encoding absent on low-cardinality columns, and page sizes far
  from useful, both add secondary overhead once the row-group-level issues
  are fixed.

The obvious way to check any of this -- open the file with a full Parquet
engine and look -- works, but pulls in a real Parquet/Arrow dependency just
to read a few dozen bytes of footer metadata. This tool reads only the
footer (see below) and turns it directly into "does this actually prune,"
not just "does a `statistics` field exist."

## Establishing the facts first

Before writing any of the checks below, this claim -- that unsorted data
defeats pruning and it's the dominant cost -- was measured, not assumed.
[`examples/measure_evidence.py`](examples/measure_evidence.py) writes real
Parquet files with `pyarrow` and queries them with `duckdb` (both dev-only
dependencies; neither is required to run this tool), with
`PRAGMA enable_profiling='json'` giving the real `total_bytes_read` DuckDB's
own Parquet reader touched. This is the real output of a fresh run:

```
=== 1. Sorted vs. unsorted: same data, same row-group size, one selective filter ===
  this tool's estimate, sorted:   prunes 19.0 of 20 row groups on average for an equality filter on an observed value (row-group ranges overlap 0% of the time pairwise)
  this tool's estimate, unsorted: prunes 0.0 of 20 row groups on average for an equality filter on an observed value (row-group ranges overlap 100% of the time pairwise)
  DuckDB, sorted:   total_bytes_read=4,598  wall=2.96ms
  DuckDB, unsorted: total_bytes_read=33,783  wall=3.01ms
  -> unsorted reads 7.3x more bytes for the identical filter

=== 2. Row group count: too many tiny groups vs. one giant group vs. a reasonable count ===
  tiny_groups (row_group_size=500): row_groups= 4000  total_bytes_read=   528,641  wall=  15.03ms  file_size=11,248,093
  huge_group (row_group_size=N, i.e. 1 group): row_groups=    1  total_bytes_read=    26,550  wall=  10.36ms  file_size=8,283,702
  normal_groups (row_group_size=100_000): row_groups=   20  total_bytes_read=     4,598  wall=   1.28ms  file_size=12,069,990

=== 3. Missing statistics ===
  with statistics: total_bytes_read=4,598  wall=1.36ms
  no statistics:   total_bytes_read=32,862  wall=1.89ms
  -> missing statistics reads 7.1x more bytes for the identical filter

=== 4. Too many small files vs. one compacted file (same total rows) ===
  200 small files: wall=5.11ms
  1 compacted file (same total rows): wall=0.98ms
  -> 5.2x slower wall time for the same query over the same rows
```

Honest caveats: these are single runs on one laptop, not a benchmark suite
-- the exact ratios will vary run to run and with row width, compression
codec, and DuckDB version. What doesn't vary is the direction and rough
scale of every effect: unsorted data, missing statistics, and pathological
row-group counts each cost several times more bytes read or wall time for
an identical query over identical row counts. Case 2's `huge_group` result
is worth calling out: a single sorted row group still reads *fewer* bytes
than 4,000 tiny sorted row groups (page-level statistics inside that one
row group let DuckDB skip most of it), but nearly 6x more than 20
well-sized ones -- both extremes are real costs, in different amounts, for
different reasons.

## Reading the footer without a Parquet engine

Like the sibling project [`parquet-schema-check`](https://github.com/agentscope-ai-java/parquet-schema-check),
this hand-rolls just enough of Apache Thrift's compact protocol to walk a
Parquet footer's `FileMetaData` struct -- see
[`thrift_compact.py`](src/parquet_layout_audit/thrift_compact.py) and
[`footer.py`](src/parquet_layout_audit/footer.py), cross-checked
field-by-field against `pyarrow`'s own metadata API in this repo's test
suite. **There is no Parquet or Thrift dependency at runtime.**

This tool reads more of the footer than a schema check needs to, though:
row group byte sizes and row counts, each column chunk's `num_values`,
compressed/uncompressed sizes, dictionary-page presence, and -- the whole
point here -- the `Statistics` struct's min/max bounds per column chunk.
Page counts come from the optional `encoding_stats` field (a per-chunk
tally of how many pages of each type the writer emitted); when a writer
doesn't record it, the page count is reported as unknown rather than
estimated by scanning page headers, which would mean reading every row
group's raw bytes and defeating the point of a footer-only tool.

## The prunability estimate

For each column, every row group with usable statistics contributes a
`[min, max]` range. The estimate is **pairwise range overlap**: for every
pair of row groups, do their ranges intersect at all? If two ranges don't
overlap, no filter value can ever match both, so a query hitting one of
them structurally can't also need the other; if they do overlap, some value
exists that would force a reader to open both.

Let `overlap_fraction` be the fraction of all row-group pairs whose ranges
intersect. A row group touched by a query is, on average, touched alongside
`(n - 1) * overlap_fraction` others (each of the other `n - 1` row groups
overlaps it with that probability, by definition), plus itself -- so the
average number of row groups a single-value equality filter must open is
`1 + (n - 1) * overlap_fraction`, and the average number **pruned** is `n`
minus that. This needs only pairwise comparison, not subtraction, so it
works identically for integers, floats, dates encoded as integers, and
byte-string columns -- there's no need to define a numeric "distance"
between two strings. It runs in `O(n log n)`: sort row groups by minimum,
then binary-search, for each one, how many later-sorted row groups have a
minimum at or below its maximum.

### Getting this wrong first

An earlier version of this estimate simulated an equality filter at each
row group's own recorded *minimum* and counted how many ranges contained
it. That measurement is biased whenever minimums and maximums cluster at
opposite ends of the domain -- which is exactly what happens when a column
is shuffled uniformly at random into fixed-size row groups: each row
group's minimum tends to land near the global minimum (the smallest of many
random samples) and its maximum near the global maximum, the same reason a
hand dealt from a shuffled deck has a good chance of holding both a very
low and a very high card. Probing only at each group's own minimum then
measures a value artificially close to the global minimum, which only a
handful of other groups' ranges also reach down to -- understating the true
overlap. On the 20-row-group shuffled file from the evidence above, that
approach reported **"prunes 9.5 of 20"** -- a plausible-looking partial win
that is simply wrong. The pairwise method correctly reports **"prunes 0.0
of 20,"** which matches what DuckDB actually does with the file: read
almost the same bytes as it would with a single row group covering
everything. This is exactly the trap the "investigate before designing"
step in this project's process caught -- and why the method above is
pairwise overlap, not per-group probing.

The estimate is still structural, not a query log: it says nothing about
which values a real workload's filters actually ask for, and it reports "not
applicable" rather than a number when fewer than two row groups have usable
statistics for a column.

## Install

```sh
pip install parquet-layout-audit
```

Zero runtime dependencies -- footer parsing is pure standard library, as
described above. `pyarrow` and `duckdb` are dev-only, used to generate and
measure test fixtures and evidence, never imported by the package itself.

## Use

```sh
parquet-layout-audit data/*.parquet
parquet-layout-audit --json data/*.parquet > report.json
parquet-layout-audit --fail-on warning data/*.parquet   # stricter CI gate
```

```python
from parquet_layout_audit import read_layout, analyze_file, analyze_dataset

layout = read_layout("orders_2024.parquet")
report = analyze_file(layout)

for column in report.columns:
    print(column.column, column.prunability.describe())

for finding in report.findings:
    print(finding.severity.value, finding.code, finding.column, finding.message)
    print("  remedy:", finding.remedy)

# Findings that only make sense across multiple files (too many small files):
layouts = [read_layout(p) for p in ("a.parquet", "b.parquet", "c.parquet")]
for finding in analyze_dataset(layouts):
    print(finding.message)
```

## What it flags

| Code | Flags | Severity |
| --- | --- | --- |
| `PLA001` | More row groups than `--max-row-groups` (default 200) -- per-row-group overhead dominates. | warning |
| `PLA002` | A single row group covering a large file (no pruning granularity possible), or any row group over `--max-row-group-bytes` (default 1 GiB). | warning |
| `PLA003` | A column with no usable statistics in one or more row groups (statistics missing entirely is more severe than partially missing); `INT96` columns are called out separately since their statistics can't be reliably decoded at all. | error / info (INT96) |
| `PLA004` | A column whose row-group ranges overlap enough that pruning is poor -- the prunability estimate above, thresholded into "effectively unsorted" and "partially clustered" bands. | warning / info |
| `PLA005` | A column with low cardinality (per `distinct_count`, when the writer recorded it) that isn't dictionary-encoded. | info |
| `PLA006` | Average page size (from `encoding_stats`, when the writer recorded it) far below or above a useful range. | info |
| `PLA007` | Dataset-level: a large fraction of the given files are small enough that per-file overhead dominates. | warning |

Every finding carries `file`, `column` (`None` for `PLA007`, which spans
files), `message` (the concrete numbers, not just "this is bad"), and
`remedy` (what to change and, where computable, its cost -- e.g. "sort by
`event_date` before writing; this file currently prunes 0.0 of 20 row
groups for that column").

## Options

| Flag | Default | What it controls |
| --- | --- | --- |
| `--json` | off | Emit a machine-readable report instead of text. |
| `--fail-on {error,warning,none}` | `error` | Minimum severity that produces a non-zero exit code. |
| `--max-row-groups` | `200` | Row groups beyond this count trigger `PLA001`. |
| `--max-row-group-bytes` | `1073741824` (1 GiB) | Row groups above this size trigger `PLA002`. |
| `--small-file-bytes` | `16777216` (16 MiB) | Files under this size count toward `PLA007`. |
| `--poor-prunability-fraction` | `0.1` | Below this fraction of row groups pruned on average, a column is "effectively unsorted" (`PLA004`, warning). |
| `--partial-prunability-fraction` | `0.5` | Below this (and at/above the poor threshold), a column is "partially clustered" (`PLA004`, info). |

Other thresholds (`large_file_min_rows`, `low_cardinality_ratio`,
`low_cardinality_max_distinct`, `tiny_page_bytes`, `huge_page_bytes`) are
exposed on `AuditOptions` in the Python API but not yet as CLI flags.

Exit codes: `0` clean (or below `--fail-on`), `1` warnings at or above the
threshold, `2` errors present, `3` usage problem (no readable files given).

## What it does not do

- **It does not read row data.** Only the footer's last
  `footer_length + 8` bytes are read; row-group pruning is estimated from
  recorded statistics, never verified by scanning actual values.
- **It does not compare schemas across files.** That's
  [`parquet-schema-check`](https://github.com/agentscope-ai-java/parquet-schema-check)'s
  job -- a column's physical/logical type drifting between files is a
  different failure mode from a well-typed column laid out badly, and this
  tool doesn't duplicate that check.
- **It does not read or lint query plans.** Whether a specific query's
  filter actually gets pushed into a scan, spills to disk, or misestimates
  cardinality is [`duckdb-plan-lint`](https://github.com/agentscope-ai-java/duckdb-plan-lint)'s
  job; this tool only looks at how a file is laid out on disk, independent
  of any particular query.
- **The prunability estimate assumes filters ask for values that actually
  appear in the file** and says nothing about which values a real
  workload's filters use, how selective they typically are, or how much
  wall-clock time pruning would actually save for a given engine.
- **`distinct_count` and `encoding_stats` are only used when the writer
  recorded them.** Measured directly: `pyarrow`'s own writer never sets
  `distinct_count` (confirmed empirically, not assumed -- see
  `tests/test_analyze.py`), so `PLA005` will rarely fire against
  `pyarrow`-written files even on genuinely low-cardinality columns; this
  is disclosed rather than worked around with a data-scanning fallback.
- **`INT96` statistics are not decoded.** The type is deprecated, and
  writers that still use it (legacy Spark/Impala) typically don't write
  usable statistics for it either -- confirmed by writing one such column
  with `pyarrow` and observing `statistics=None`.
- **It does not compact files, rewrite row groups, or resort data.** It
  tells you what to change and estimates the cost of not changing it; it
  doesn't change anything.
- **Bloom filters and column/offset indexes are not parsed.** They can
  also affect pruning, but adding them here would mean reading structures
  outside the plain footer -- next candidate for a future version, not
  silently assumed absent.
